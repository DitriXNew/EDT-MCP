# delete_metadata

Delete a metadata object or member (FQN-addressed). DESTRUCTIVE and CASCADING: on the md-refactoring path EDT cleans the REFERENCES to the deleted object across BSL, forms and metadata - the referring objects themselves are NOT deleted. Two-phase: call once WITHOUT confirm to preview what will be removed, then again with confirm=true to apply. A reference EDT cannot auto-clean leaves the delete BLOCKED and lists the referring objects; an EDT platform prohibition is listed separately and also blocks. force=true overrides either block and leaves only genuine incoming references dangling. EXCEPTION - an owned FORM object, a FORM member or an XDTO package member is removed straight from its container: NOTHING blocks it (force is ignored) and no cross-object cascade runs, so references from elsewhere (a field's dataPath, a command, an XDTO type) are left broken - re-check with get_metadata_details (find_references takes TOP-level FQNs only, not these members). Parameters and examples: get_tool_guide('delete_metadata').

## Parameters
| Parameter | Required | Type | Description |
| --- | --- | --- | --- |
| projectName | yes | string | EDT project name (required). |
| fqn | yes | string | Full-name FQN of the node to delete (required), e.g. 'Catalog.Products' or 'Document.SalesOrder.Attribute.Amount' (type / kind tokens may be English or Russian; the Name parts are the programmatic Name, not the synonym). |

## Guide
Deletes one metadata node (a top-level object or one of its members) addressed by a 1C full-name FQN. A top-level object, and equally an mdclass MEMBER of one (attribute / tabular section / dimension / resource / enum value), is deleted through EDT's md-refactoring service - the same reference cleanup EDT computes for the IDE delete - which cascades across the configuration: BSL code, forms and other metadata. It cascades what it CAN clean; an incoming reference it cannot auto-clean does not get rewritten - it BLOCKS the delete instead (or is left dangling if you pass `force`). EDT may also report a platform prohibition; that blocks independently and is never described or counted as an incoming reference. A member that lives inside another object's own content (an owned form OBJECT, a form MEMBER, an XDTO package MEMBER) is removed from that container directly, WITHOUT a cross-object reference cascade - see the per-kind sections below for what each does and does not clean up. The target's identity is its programmatic Name (not its synonym). Replaces the former delete_metadata_object.

## Think twice
This is a CASCADING, hard-to-reverse deletion: a wrong target can mass-edit BSL, forms and metadata across the whole configuration. Always preview first, run it on a configuration you can revert (version control), and do not execute without an explicit request. After execute, verify with get_project_errors.

## When to use
Use to remove an existing node and have EDT clean up the references it can: that covers a top-level object AND its mdclass members (attribute / tabular section / dimension / resource / enum value). A form object, a form member and an XDTO package member are removed from their own container instead, with no CROSS-object cascade (only the owner's own pointers, such as a default-form setting, are cleaned) - see their sections below. To rename instead use rename_metadata_object; to create use create_metadata.

## Two-phase workflow
1. Preview (confirm omitted / false): returns the refactoring title and items, then splits EDT's problems. Genuine incoming references (`CleanReferenceProblem`) are listed under `blockingReferences` / `blockingReferencesCount`; every other problem is a platform prohibition under `platformProhibitions` / `platformProhibitionsCount`. Either category sets `blocking=true`, and a confirm=true delete would be refused unless force=true. Nothing is modified.
2. Execute (confirm=true): performs the delete refactoring. If either category is non-empty and force is not set, the delete is REFUSED with action='blocked' and both categories remain separate (nothing is changed). Otherwise returns action='executed'.

## Reference blocking and force
`confirm` and `force` are independent. `confirm` is the preview gate (it decides preview vs execute). `force` overrides either an incoming-reference block or a platform prohibition. With no force, an incoming reference EDT cannot auto-clean (e.g. a Catalog still used as another object's attribute Type) or any separately listed platform prohibition returns action='blocked', success=false. With `force=true`, the node is removed; only genuine incoming references are described as DANGLING, while platform prohibitions are described as overridden. Prefer resolving either condition first; force is a last resort. References the refactoring CAN auto-clean (BSL usages, form bindings) never block - they are cleaned automatically.

The existing `blockingReferences` / `blockingReferencesCount` contract remains reference-only; it is not repurposed as an aggregate problem list. `affectedReferences` / `affectedReferencesCount` remain exact deprecated aliases of those reference-only fields for wire compatibility. Clients that need every blocking condition must read both the reference fields and `platformProhibitions` / `platformProhibitionsCount`.

After a forced md-refactoring delete, the tool waits for export and reads the registering `.mdo` (`src/Configuration/Configuration.mdo` for a top object, or the owning top object's `.mdo` for a member). If that file still registers the deleted node, or cannot be verified, the model change remains a successful `action='executed'` result but is explicitly partial: `persisted=false`, `registeringFile`, and `registeringContainer` name the stale/unverified on-disk half. A verified completed delete keeps the existing response shape with no extra fields.

## Parameter details
- `projectName` (required) - EDT project name.
- `fqn` (required) - the delete target. Top object: 'Type.Name' (e.g. 'Catalog.Products' deletes the whole catalog). Member: 'Type.Name.Kind.Name', including a NESTED member (e.g. 'Catalog.X.TabularSection.T.Attribute.A'). Any node create_metadata can address - an attribute / tabular section / dimension / resource / enum value / command / template / recalculation / type-specific child - can be deleted by its FQN.
- `confirm` (optional, default false) - false previews, true applies.
- `force` (optional, default false) - on confirm=true, delete despite blocking incoming references or platform prohibitions. Incoming references are left dangling; prohibitions are overridden. Does nothing in preview.

## Form object
An owned form OBJECT is addressed by the SAME 4-part FQN create_metadata uses to make it: `Catalog.X.Form.FormName` (the form token is bilingual - `Form` / `Forms` / `Форма` / `Формы`). Deleting it removes the form from its owner's `forms` collection AND its content `Form.form`, and clears any default-form setting on the owner that pointed at it (`defaultObjectForm` / `defaultListForm` / ...), so no dangling reference is left. The same two-phase preview/confirm applies (preview lists the form as a single `{name, type}` item, `blockingReferencesCount` is 0). `force` is ignored (an owned form never blocks). The change persists to the owner `.mdo` on disk. A `CommonForm.Name` is NOT an owned form - it is a real top object, deleted through the normal cascading refactoring path above.

## Form members
A FORM member is addressed like its create/modify FQN: `Catalog.X.Form.F.<Kind>.Name` (or `CommonForm.F.<Kind>.Name`), Kind = Attribute / Command / Parameter / Field / Button / Group / Decoration / Table, a COLUMN of a collection-typed attribute (`...Attribute.AttrName.Column.ColName`), or an event Handler (`...Form.F.Handler.Event`, item-level `...Field.Item.Handler.Event`). The `<Kind>` segment is part of the ADDRESS, not a hint: the member must really be of that kind. An FQN naming another kind (`...Button.PriceField` for a FIELD) or a misspelt one (`...Fielld.PriceField`) resolves to nothing and is refused, and the error names the kind the same-named element actually has plus the corrected FQN. A kind token addresses its EClass AND its subclasses, so the designer's own children have exactly one supported address too: an AutoCommandBar / ContextMenu / actions panel IS a Group (`...Group.FormCommandBar`), an ExtendedTooltip IS a Decoration (`...Decoration.PriceExtendedTooltip`). A table addition (search string / view status / search control) is the one element no kind token names, so no FQN addresses it: it is created and removed together with its table. For an item-level handler the OWNER's kind segment is resolved the same way. The same two-phase preview/confirm applies; deleting a Group / Table cascades its contained subtree. Unlike the mdclass path there is NO reference cascade for forms: a cross-reference to the removed member (a field's dataPath, a button's command) is NOT rewritten - re-check with get_metadata_details afterwards. The change persists to the form's `Form.form` on disk. For a form member the preview's `items` list the removed element + its contained descendants as `{name, type}` and `blockingReferencesCount` is 0 (no cascade is computed for forms). `force` has no effect on form-member deletes: form members never block (there is no reference cascade to refuse), so the flag is simply ignored.
## Predefined items (`Catalog` / `ChartOfCharacteristicTypes` / `ChartOfCalculationTypes` / `ChartOfAccounts`)
A predefined item is addressed by the SAME FQN create_metadata / modify_metadata use: `Catalog.X.Predefined.ItemName`, `ChartOfCharacteristicTypes.X.Predefined.ItemName`, `ChartOfCalculationTypes.X.Predefined.ItemName` or `ChartOfAccounts.X.Predefined.AccountName`. The same two-phase preview/confirm applies. Deleting a FOLDER item (or, for a `ChartOfAccounts`, a PARENT account) cascades ALL its nested items / child accounts (recursively, via the account hierarchy) - the preview's `items` array lists the item AND every cascaded descendant (name + kind), and the message reports the count, so check it before confirming. Unlike a form member, a predefined item DOES get an incoming-reference check: the preview and a confirm=true call both scan for incoming references to the item AND (for a folder, or a ChartOfAccounts parent account) every cascaded descendant, by REUSING find_references' OWN full metadata+BSL reference-collection engine - so it covers both METADATA cross-references (e.g. a DynamicList filter, another object's default value, a ChartOfCalculationTypes item's base/displaced/leading pointing at a sibling calc type, or a ChartOfAccounts ExtDimensionType's characteristicType pointing at a ChartOfCharacteristicTypes predefined item) AND a BSL symbolic use found via the same Xtext scan find_references uses. Only ONE narrow case is excluded on top of that: a reference whose source is the item's OWN owner AND whose feature is exactly the structural predefined-data-source linkage (a derived-model back-reference that exists merely because the item lives inside that owner, not a real dependency) - find_references itself does NOT apply this exclusion (it intentionally shows such self-references in its own diagnostic view). Any OTHER same-owner reference (e.g. an attribute's fill value pointing at a sibling item in the same catalog) still BLOCKS like any other reference. If the BSL half of the scan cannot be verified (the Xtext reference index is unavailable, or the scan throws), the check FAILS CLOSED: the reference state is treated as UNVERIFIED and a confirm=true delete is BLOCKED the same as a genuine reference, unless `force=true`. A non-empty `blockingReferences` (or an unverified scan) on confirm=true BLOCKS the delete unless `force=true`; force proceeds and leaves those references dangling (reported in the message and under `blockingReferences`/`blockingReferencesCount`, with `forced=true`). The change persists to the OWNER's `.mdo` (the predefined content is a plain containment on the owner, not a separate resource). The item may be addressed by either the normalized or the original `ё` spelling of its Name (exact-first, then a yo-normalized retry).

## XDTO package members
An XDTO member is addressed like its create/modify FQN: `XDTOPackage.<Package>.ObjectType.<Name>`, `XDTOPackage.<Package>.Property.<Name>` (a package-global property) or `XDTOPackage.<Package>.ObjectType.<Type>.Property.<Name>`. The same two-phase preview/confirm applies; deleting an `ObjectType` removes it AND all its own properties. Like a form member and unlike the mdclass path, this branch edits the package's own content model directly, so there is **no cross-object reference cascade**: a cross-reference to the removed member (a `Property` whose type or ref points at the deleted `ObjectType`, in this or another package) is NOT rewritten and does NOT block - the preview reports `blocking=false` with an empty `blockingReferences`, and `force` has no effect. Re-check afterwards with `get_metadata_details` on the package, or `validate_xdto_package` (`XDTOPackage.<Name>`), which reports EDT's own validation for exactly this. The change persists to the package `.mdo` and its sibling content resource on disk.

## Bilingual (ru/en)
Resolves by the programmatic Name; only the leading TYPE token and the child KIND tokens are dialect-aware (English or Russian). The synonym is never used to locate the target.

## Examples
- Preview: `{projectName: 'P', fqn: 'Catalog.Products'}`
- Execute: `{projectName: 'P', fqn: 'Catalog.Products', confirm: true}`
- Delete one attribute: `{projectName: 'P', fqn: 'Document.SalesOrder.Attribute.Amount', confirm: true}`
- Force-delete a still-referenced object (leaves danglers): `{projectName: 'P', fqn: 'Catalog.Products', confirm: true, force: true}`

## Gotchas
- A malformed nested FQN with an odd trailing token (e.g. 'Catalog.Products.Attribute') is rejected as not found, so a nested delete never silently falls back to the parent.
- Deletion targets the programmatic Name; passing a synonym will not resolve.
- On a forced md-refactoring delete, `success=true` describes the completed model change; check `persisted` / `registeringFile` before treating the on-disk half as complete.

## Predefined items

A PREDEFINED item is checked for incoming references exactly like an ordinary object, and the same two-phase preview/confirm applies.

## Members removed from their own container

An owned FORM object, a FORM member and an XDTO package member are removed from their own container instead: nothing blocks them (force is ignored), and no CROSS-object cascade runs - a reference from elsewhere (a field's dataPath, a Property whose type points at the deleted ObjectType) is NOT rewritten, so re-check with get_metadata_details.

Only the owner's own pointers are cleaned: deleting an owned form clears the default-form settings that named it.
