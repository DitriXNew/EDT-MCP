# delete_metadata

Delete a metadata object or member (FQN-addressed). DESTRUCTIVE and CASCADING: on the md-refactoring path EDT cleans the REFERENCES to the deleted object across BSL, forms and metadata - the referring objects themselves are NOT deleted. Two-phase: call once WITHOUT confirm to preview what will be removed, then again with confirm=true to apply. A reference EDT cannot auto-clean leaves the delete BLOCKED and lists the referring objects; an EDT platform prohibition is listed separately and also blocks. force=true overrides either block and leaves only genuine incoming references dangling, but never vendor support: a delete touching an object whose support rule forbids changes is refused. EXCEPTION - an owned FORM object, a FORM member or an XDTO package member is removed straight from its container: nothing else blocks it (force is ignored) and no cross-object cascade runs, so references from elsewhere (a button's command, an XDTO type) are left broken - re-check with get_metadata_details (find_references takes TOP-level FQNs only, not these members). Use operations for atomic deletes of members of one form; preview the complete batch before confirming. Parameters and examples: get_tool_guide('delete_metadata').

## Guide
Deletes one metadata node (a top-level object or one of its members) addressed by a 1C full-name FQN. A top-level object, and equally an mdclass MEMBER of one (attribute / tabular section / dimension / resource / enum value), is deleted through EDT's md-refactoring service - the same reference cleanup EDT computes for the IDE delete - which cascades across the configuration: BSL code, forms and other metadata. It cascades what it CAN clean; an incoming reference it cannot auto-clean does not get rewritten - it BLOCKS the delete instead (or is left dangling if you pass `force`). EDT may also report a platform prohibition; that blocks independently and is never described or counted as an incoming reference. A member that lives inside another object's own content (an owned form OBJECT, a form MEMBER, an XDTO package MEMBER) is removed from that container directly, WITHOUT a cross-object reference cascade - see the per-kind sections below for what each does and does not clean up. The target's identity is its programmatic Name (not its synonym). Replaces the former delete_metadata_object.

## Think twice
This is a CASCADING, hard-to-reverse deletion: a wrong target can mass-edit BSL, forms and metadata across the whole configuration. Always preview first, run it on a configuration you can revert (version control), and do not execute without an explicit request. After execute, verify with get_project_errors.

## When to use
Use to remove an existing node and have EDT clean up the references it can: that covers a top-level object AND its mdclass members (attribute / tabular section / dimension / resource / enum value). A form object, a form member and an XDTO package member are removed from their own container instead, with no CROSS-object cascade (only the owner's own pointers, such as a default-form setting, are cleaned) - see their sections below. To rename instead use rename_metadata_object; to create use create_metadata.

## Two-phase workflow
Echoes, previews, follow-up hints and write refusals use canonical English type/member tokens with unchanged programmatic Names. Scope hashes include this canonical address and the removal scope, so equivalent Russian/English spellings yield the same token.

1. Preview (confirm omitted / false): returns the refactoring title and items, then splits EDT's problems. Genuine incoming references (`CleanReferenceProblem`) are listed under `blockingReferences` / `blockingReferencesCount`; every other problem is a platform prohibition under `platformProhibitions` / `platformProhibitionsCount`. Either category sets `blocking=true`, and a confirm=true delete would be refused unless force=true - except a vendor-support lock (a prohibition with `supportLock=true`), which force does not override. Nothing is modified.
2. Execute (confirm=true): performs the delete refactoring. If either category is non-empty and force is not set, or any prohibition is a vendor-support lock, the delete is REFUSED with action='blocked' and both categories remain separate (nothing is changed). Otherwise returns action='executed'.

## Nested subsystems
Address a nested subsystem by its whole chain from a top-level subsystem: `Subsystem.<Parent>.Subsystem.<Child>`, repeated to any depth, exactly as list_subsystems prints it. Every type token may independently be English or Russian (for example `Subsystem.Sales.Подсистема.Orders`); each name is the stored programmatic Name, never a synonym. A bare `Subsystem.<Name>` addresses only a top-level subsystem. Nested chains have no `ё`-to-`е` retry.

The same preview/confirm workflow and md-refactoring reference cleanup apply. The preview includes EDT's refactoring title and removal items for the addressed subsystem, without changing the model or disk. A confirmed delete lets EDT clean the parent's bare-name `<subsystems>` registration and exports that parent's own `.mdo`; for `Subsystem.Sales.Subsystem.Orders` that is `src/Subsystems/Sales/Sales.mdo`. The child's own `.mdo` is removed by EDT's refactoring. `Configuration.mdo` lists only top-level subsystems and its registration list is unchanged by a nested delete. The response names the canonical chain using the stored names and English type tokens.

Deleting a subsystem removes all its nested subsystems, whether the addressed parent is top-level or nested. The preview message lists every nested descendant by its whole chain FQN, even when EDT's removal items name only the parent. The confirmation consent also lists the nested subsystems and counts them with the addressed subsystem. Confirming delegates the whole cascade, including descendant folders and files, to EDT's delete refactoring. A chain whose stored parent links disagree with its address is refused; check the links in EDT and verify the chain with list_subsystems before retrying.

## Vendor support
A configuration received from a vendor (the `.distr` support settings) can lock objects: their support rule does not allow changes. The tool asks EDT whether the target may be deleted BEFORE any refactoring is built, for preview and confirm alike: a locked target (or, for a form member, a predefined item or an XDTO member, a locked owning object) is refused with success=false, the error names the object, and nothing is changed. When the target itself may be deleted but the refactoring would have to change a locked object (a referencing object, the configuration), EDT reports it as a platform prohibition; the tool re-checks that object and marks the entry `supportLock=true`. Deleting an attribute of a top object also removes that object's derived field, which EDT judges as deleting the object itself, so in a configuration whose root is locked such a delete is blocked even when the object and the attribute are editable. A delete with any `supportLock=true` entry is blocked even with `force=true`. Other platform prohibitions keep the force behaviour described below. The way out is a configuration extension (adopt the object with adopt_metadata_object and change the adopted copy) or the user allowing changes in EDT's support settings; this server never changes support settings. A configuration extension and an external data processor/report project are never under vendor support: EDT applies support only to a configuration's own (native) root, never inside an extension, which is why an extension is the way to change a supported configuration.

## Reference blocking and force
`confirm` and `force` are independent. `confirm` is the preview gate (it decides preview vs execute). `force` overrides either an incoming-reference block or a platform prohibition. With no force, an incoming reference EDT cannot auto-clean (e.g. a Catalog still used as another object's attribute Type) or any separately listed platform prohibition returns action='blocked', success=false. With `force=true`, the node is removed; only genuine incoming references are described as DANGLING, while platform prohibitions are described as overridden. Prefer resolving either condition first; force is a last resort. Force never overrides vendor support (next section). References the refactoring CAN auto-clean (BSL usages, form bindings) never block - they are cleaned automatically.

The existing `blockingReferences` / `blockingReferencesCount` contract remains reference-only; it is not repurposed as an aggregate problem list. `affectedReferences` / `affectedReferencesCount` remain exact deprecated aliases of those reference-only fields for wire compatibility. Clients that need every blocking condition must read both the reference fields and `platformProhibitions` / `platformProhibitionsCount`.

After a forced md-refactoring delete, the tool waits for export and reads the registering `.mdo` (`src/Configuration/Configuration.mdo` for a top object, or the owning top object's `.mdo` for a member). If that file still registers the deleted node, or cannot be verified, the model change remains a successful `action='executed'` result but is explicitly partial: `persisted=false`, `registeringFile`, and `registeringContainer` name the stale/unverified on-disk half. A verified completed delete keeps the existing response shape with no extra fields.

## Parameter details
- `projectName` (required) - EDT project name.
- `fqn` (required unless `operations` is provided) - the delete target. Top object: 'Type.Name' (e.g. 'Catalog.Products' deletes the whole catalog). Member: 'Type.Name.Kind.Name', including a NESTED member (e.g. 'Catalog.X.TabularSection.T.Attribute.A'). Any node create_metadata can address - an attribute / tabular section / dimension / resource / enum value / command / template / recalculation / type-specific child - can be deleted by its FQN.
- `operations` (alternative to `fqn`) - 1..100 `{action: "delete", fqn: "..."}` objects addressing members of ONE form. See the atomic batch contract below.
- `atomic` (batch only, default true) - must be true. Non-atomic execution is not supported.
- `confirm` (optional, default false) - false previews, true applies.
- `force` (optional, default false) - on confirm=true, delete despite blocking incoming references or platform prohibitions. Incoming references are left dangling; prohibitions are overridden - except a vendor-support lock, which is never overridden. Does nothing in preview.
- `timeout` (optional, default 420) - how long to wait for the UI-thread delete work, in seconds, clamped to 60..3600. It does NOT cover the pre-flight cascade settle, which has its own separate 60s bound. Raise it for a very large configuration; the default can also be changed in Preferences > MCP Server > Tools > `delete_metadata`.

## Timeout, and what the model is left in
This section describes single-`fqn` calls. A batch rejects `timeout` and waits for its UI work to finish; an HTTP client disconnect does not cancel EDT work. Inspect the form before retrying a disconnected call.

The delete work runs on EDT's UI thread and cannot be preempted, so `timeout` bounds only how long the CALL waits - it does not stop work that has started. The pre-flight cascade settle runs first on the caller thread under its existing separate 60s bound and is not counted against `timeout`.

- If the delete never STARTED (the deadline elapsed while its UI-thread work was still queued and cancelling it kept it from starting), NOTHING was deleted, the model is untouched, and no check or cleanup is needed. Retry when EDT's job scheduler is less busy or raise `timeout`.
- A PREVIEW (`confirm` omitted / false) never writes on any branch. If it times out, nothing was deleted and the model is unchanged; EDT may still finish computing that preview, but there is no mutation to inspect or clean up.
- Once a `confirm=true` call has started, a timeout or interruption stops only the wait. EDT may still finish the delete, and the target or part of its reference-cleanup cascade may already be applied. The error carries `mutationOutcomeUnknown:true` (or `mutationCommitted:true` when a write was already observed), which is the structural signal to automated callers that a re-read is mandatory. Before retrying, call `get_metadata_details` on the target FQN; for a top-level target, also call `get_metadata_objects` for its metadata type. Do not assume anything was undone, and do not repeat the delete until those calls establish whether the target remains.

## Atomic single-form batch

Use `operations` instead of `fqn` to delete a group and related form commands with one model write and one form export:

```json
{
  "projectName": "ERP2",
  "operations": [
    {"action": "delete", "fqn": "Document.Transfer.Form.Main.Group.Indicators"},
    {"action": "delete", "fqn": "Document.Transfer.Form.Main.Command.TransferMaterials"},
    {"action": "delete", "fqn": "Document.Transfer.Form.Main.Command.WriteOffWork"}
  ],
  "atomic": true
}
```

Preview the complete batch, then repeat with `confirm:true` to apply it. The existing destructive-consent gate covers all targets and their contained descendants. The form is loaded once per read/write boundary; the whole scope is rechecked after consent and before the first removal. Any change to that scope refuses the write. Identical/overlapping targets are refused with `dependsOnPriorOperation`; keep only the containing target or remove the duplicate.

The supported subset is form items (including groups and their descendants), commands, parameters and handlers in one form. Attribute/column deletes, whole-form/top-object deletes, multiple forms, create/modify actions, `atomic:false`, `force:true`, `timeout`, `continueOnError` and unknown top-level/operation fields are refused before any mutation. Type/kind tokens use the same bilingual resolvers as a single delete; Name parts remain programmatic identifiers. This v1 does not support a `create A -> modify A` dependency chain; it refuses that batch without executing either item.

Whole-request preflight returns all independent input/target errors under `errors`, with zero-based `operationIndex` (`-1` means the request), `reason` and actionable `error`. It returns `applied:[]`, `committed:false`, `persistenceState:"unchanged"`; nothing is changed. Each target and its removal scope are checked again inside the one BM write transaction. A failure of operation N escapes that task, rolling back earlier removals: the response names `failedOperationIndex`, its exact reason, `rollbackPerformed:true`, `applied:[]` and the unchanged remaining state.

A completed model commit returns all operation indexes under `applied`, `committed:true`, `rollbackPerformed:false`, and `items` including the contained removal scope. Model atomicity does not imply atomic disk export. `exportSubmitted` only says the export was queued; `persistenceState` distinguishes `exportNotSubmitted`, `exportUnobservable` and `exportDrainedBytesUnverified`. Even a drained queue does not prove the bytes: inspect `Form.form` and read the form back. The shared written-object marker report (`markersIncomplete`, optional `markersIncompleteReason`, `markerCount`, `markers`) follows the export barrier, just as for create/modify.

An export-barrier refusal preserves `applied`, `committed`, `items`, `remainingState` and `safeRetry`, adds `mutationCommitted:true`, and reports `persistenceState:"unconfirmed"`. Never repeat applied operations blindly. An opaque commit/export exception carries `mutationOutcomeUnknown:true` and `possibleApplied` (or the stronger known `mutationCommitted:true` and `applied`); inspect every target and disk before retrying. External cross-references retain the existing single-member semantics: they are not rewritten; deleting a command may leave a surviving button's reference broken. Re-check form details and markers.

Mixed create/modify/delete transactions, non-atomic continuation and cross-container atomicity remain future scope. Build-progress diagnostics belong to #336 and are not changed here.

The 420s default uses the same evidence as rename: both operations run through the same md-refactoring/UI-thread machinery, whose worst measured legitimate completion took 301s while EDT waited out its own derived-data timeout. Lowering the bound risks reporting failure while a healthy destructive cascade continues in the background; raise it only when the workspace legitimately needs longer.

## Form object
An owned form OBJECT is addressed by the SAME 4-part FQN create_metadata uses to make it: `Catalog.X.Form.FormName` (the form token is bilingual - `Form` / `Forms` / `Форма` / `Формы`). Deleting it removes the form from its owner's `forms` collection AND its content `Form.form`, and clears any default-form setting on the owner that pointed at it (`defaultObjectForm` / `defaultListForm` / ...), so no dangling reference is left. The same two-phase preview/confirm applies (preview lists the form as a single `{name, type}` item, `blockingReferencesCount` is 0). `force` is ignored (an owned form never blocks). The change persists to the owner `.mdo` on disk. The form's resource folder (`src/<Type>/<Owner>/Forms/<FormName>/`) is removed by a background workspace job, and the message ends with what became of it: removed from disk; not found on disk; kept, because a form of the same name was created again before the job ran; still being removed in the background (re-check it shortly); or could not be removed (check it manually). A `CommonForm.Name` is NOT an owned form - it is a real top object, deleted through the normal cascading refactoring path above.

## Form members
A FORM member is addressed like its create/modify FQN: `Catalog.X.Form.F.<Kind>.Name` (or `CommonForm.F.<Kind>.Name`), Kind = Attribute / Command / Parameter / Field / Button / Group / Decoration / Table, a COLUMN of a collection-typed attribute (`...Attribute.AttrName.Column.ColName`) or an [additional column](#additional-columns), or an event Handler (`...Form.F.Handler.Event`, item-level `...Field.Item.Handler.Event`). `<Kind>` must match: a wrong (`...Button.PriceField` for a FIELD) or misspelt kind (`...Fielld.PriceField`) is refused with the actual kind and corrected FQN. Kind tokens include subclasses: an AutoCommandBar / ContextMenu / actions panel IS a Group (`...Group.FormCommandBar`), an ExtendedTooltip IS a Decoration (`...Decoration.PriceExtendedTooltip`). A table addition (search string / view status / search control) is the one element no kind token names, so no FQN addresses it: it is created and removed together with its table. For an item-level handler the OWNER's kind segment is resolved the same way. The same two-phase preview/confirm applies; deleting a Group / Table cascades its contained subtree. A form ATTRIBUTE (or a column of one) is deleted by EDT's own form-attribute service, the delete the form designer runs: the items EDT binds to the attribute go with it TOGETHER WITH everything inside them (a bound table's buttons, decorations and fields, whatever those are bound to); deleting a COLUMN also drops the owner's additional columns whose table path starts with the column's; the attribute's separately stored extInfo object (a dynamic list's settings, a chart, a planner) is detached with it and EDT's own export deletes its file (e.g. `ListSettings.dcss`) - the delete uses EDT's global editing context, so an open form editor saves all its unsaved changes and loses its undo history; the preview's entry names that `file` with `deletedFromDisk: true`, the response's entry carries `file` and `fileRemoval` as observed on disk after the export: REMOVED (not on disk), or STILL_PRESENT / UNVERIFIED (the file is still there, or could not be resolved or checked), which also make the result partial (`persisted: false`), as does a `Form.form` that still declares the attribute (or cannot be read) after the export; EDT may also clear the data path of a surviving item whose path stops resolving, and drop the choice-parameter links of a surviving field whose path points into the attribute or stops resolving; the form root's extInfo is kept even when the MAIN attribute is deleted - validate_form_model then reports `orphan-form-ext-info`. The preview runs EDT's own item collector and lists, the first 50 of each with exact counts in the message: the picked items as `{name, type, dataPath}`, the members inside them with `contained: true`, the dropped additional columns with their `tablePath`, and the detached object as `{name: <feature>, type, extInfo, detached: true, file, deletedFromDisk}`; it does not predict the cleared paths or the dropped links (its message says when a surviving field has links). The attribute/column preview returns `contentHash` for the full removal scope, including unlisted members and detached objects/files. Pass it as `expectedHash` with `confirm=true`: a changed scope is refused before consent or writing, including with session consent. The token is optional (rename requires it only for `disableIndices`): omitted/blank means confirm recomputes and authorizes the current scope; a separate preview alone fixes nothing. A second scope check protects consent-to-write changes. On refusal, preview again and pass the new hash. Unrelated form edits do not invalidate it; surviving items' cleared paths/links are outside this scope. Other targets ignore `expectedHash`. Its response lists what was actually observed, in the same shape, plus the kept items whose path was cleared, with `unbound: true`, and each dropped choice-parameter link as `{name, type, field, dataPath}`. In a form adopted by an extension, an attribute adopted from the base form keeps its bound items, as EDT does. When EDT's service or collector is unavailable, the preview and the delete are refused and nothing changes. Any OTHER form member has NO reference cascade: a cross-reference to it (a button's command) is NOT rewritten - re-check with get_metadata_details afterwards. The change persists to the form's `Form.form` on disk; when that export cannot be queued the response carries `persisted: false`. Form-member preview `items` include the element and its descendants as `{name, type}`, plus the attribute's scope above. `blockingReferencesCount` is 0; `force` is ignored.
## Predefined items (`Catalog` / `ChartOfCharacteristicTypes` / `ChartOfCalculationTypes` / `ChartOfAccounts`)
A predefined item is addressed by the SAME FQN create_metadata / modify_metadata use: `Catalog.X.Predefined.ItemName`, `ChartOfCharacteristicTypes.X.Predefined.ItemName`, `ChartOfCalculationTypes.X.Predefined.ItemName` or `ChartOfAccounts.X.Predefined.AccountName`. The same two-phase preview/confirm applies. Deleting a FOLDER item (or, for a `ChartOfAccounts`, a PARENT account) cascades ALL its nested items / child accounts (recursively, via the account hierarchy) - the preview's `items` array lists the item AND every cascaded descendant (name + kind), and the message reports the count, so check it before confirming. Unlike a form member, a predefined item DOES get an incoming-reference check: the preview and a confirm=true call both scan for incoming references to the item AND (for a folder, or a ChartOfAccounts parent account) every cascaded descendant, by REUSING find_references' OWN full metadata+BSL reference-collection engine - so it covers both METADATA cross-references (e.g. a DynamicList filter, another object's default value, a ChartOfCalculationTypes item's base/displaced/leading pointing at a sibling calc type, or a ChartOfAccounts ExtDimensionType's characteristicType pointing at a ChartOfCharacteristicTypes predefined item) AND a BSL symbolic use found via the same Xtext scan find_references uses. Only ONE narrow case is excluded on top of that: a reference whose source is the item's OWN owner AND whose feature is exactly the structural predefined-data-source linkage (a derived-model back-reference that exists merely because the item lives inside that owner, not a real dependency) - find_references itself does NOT apply this exclusion (it intentionally shows such self-references in its own diagnostic view). Any OTHER same-owner reference (e.g. an attribute's fill value pointing at a sibling item in the same catalog) still BLOCKS like any other reference. If the BSL half of the scan cannot be verified (the Xtext reference index is unavailable, or the scan throws), the check FAILS CLOSED: the reference state is treated as UNVERIFIED and a confirm=true delete is BLOCKED the same as a genuine reference, unless `force=true`. A non-empty `blockingReferences` (or an unverified scan) on confirm=true BLOCKS the delete unless `force=true`; force proceeds and leaves those references dangling (reported in the message and under `blockingReferences`/`blockingReferencesCount`, with `forced=true`). The change persists to the OWNER's `.mdo` (the predefined content is a plain containment on the owner, not a separate resource). The item may be addressed by either the normalized or the original `ё` spelling of its Name (exact-first, then a yo-normalized retry).

## XDTO package members
An XDTO member is addressed like its create/modify FQN: `XDTOPackage.<Package>.ObjectType.<Name>`, `XDTOPackage.<Package>.Property.<Name>` (a package-global property) or `XDTOPackage.<Package>.ObjectType.<Type>.Property.<Name>`. The same two-phase preview/confirm applies; deleting an `ObjectType` removes it AND all its own properties. Like a form member and unlike the mdclass path, this branch edits the package's own content model directly, so there is **no cross-object reference cascade**: a cross-reference to the removed member (a `Property` whose type or ref points at the deleted `ObjectType`, in this or another package) is NOT rewritten and does NOT block - the preview reports `blocking=false` with an empty `blockingReferences`, and `force` has no effect. Re-check afterwards with `get_metadata_details` on the package, or `validate_xdto_package` (`XDTOPackage.<Name>`), which reports EDT's own validation for exactly this. The change persists to the package `.mdo` and its sibling content resource on disk.

## Bilingual (ru/en)
Resolves by the programmatic Name; only the leading TYPE token and the child KIND tokens are dialect-aware (English or Russian). The synonym is never used to locate the target.

## Examples
- Preview: `{projectName: 'P', fqn: 'Catalog.Products'}`
- Execute: `{projectName: 'P', fqn: 'Catalog.Products', confirm: true}`
- Delete one attribute: `{projectName: 'P', fqn: 'Document.SalesOrder.Attribute.Amount', confirm: true}`
- Force-delete a still-referenced object (leaves danglers): `{projectName: 'P', fqn: 'Catalog.Products', confirm: true, force: true}`

## Gotchas
- A malformed nested FQN with an odd trailing token (e.g. 'Catalog.Products.Attribute') is rejected as not found, so a nested delete never silently falls back to the parent.
- Deletion targets the programmatic Name; passing a synonym will not resolve.
- On a forced md-refactoring delete, `success=true` describes the completed model change; check `persisted` / `registeringFile` before treating the on-disk half as complete.

## Predefined items

A PREDEFINED item is checked for incoming references exactly like an ordinary object, and the same two-phase preview/confirm applies.

## Members removed from their own container

An owned FORM object, a FORM member and an XDTO package member are removed from their container: nothing blocks them (force is ignored), and references elsewhere are NOT rewritten - re-check with get_metadata_details.

Only the owner's own pointers are cleaned: deleting an owned form clears the default-form settings that named it.

## External data source members

Cube members use `...Cube.C.DimensionTable.DT(.Field.F)`, `...Cube.C.Dimension.D` and `...Cube.C.Resource.R` (including Russian tokens). DimensionTable registration is checked in the Cube's `.mdo`; its fields are checked in `Cubes/C/DimensionTables/DT/DT.mdo` under `fields`. Dimensions and resources are checked inline in the Cube's file.

Use `ExternalDataSource.E.Table.T`, `...Table.T.Field.F`, `ExternalDataSource.E.Function.Fn` or `...Cube.C` (Russian tokens also work). The delete runs EDT's delete refactoring on that node, also for a source that still has Tables or Cubes, then exports the file that registers the node: the source's `.mdo` for a Table, Cube or Function, the Table's `.mdo` for a Field. Deleting a Table removes its `<tables>` line from the source's `.mdo` and its `Tables/T/` folder; deleting a source that still has Tables and Cubes removes the whole `src/ExternalDataSources/E/` directory, child files included. A forced delete then checks that file as described above. See the create_metadata guide, "External data source structure", for defaults, layout and boundaries.

## Additional columns
An additional column of an object attribute's tabular section is deleted by `...Form.F.Attribute.Object.Column.<TabularSection>.<Name>` with the same preview/confirm. EDT's designer delete takes its bound items along, and the `<additionalColumns>` entry goes with its last column. Details: get_tool_guide('create_metadata', section='Additional columns').
