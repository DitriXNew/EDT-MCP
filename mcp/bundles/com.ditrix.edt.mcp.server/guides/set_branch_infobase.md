Attach or detach an EXISTING infobase (application) to/from a specific git branch **context**, so `list_git_branches`' "Application Bindings" section and `switch_git_branch`'s automatic binding follow that branch. This tool never creates an infobase - the application must already exist (`get_applications` / `create_infobase`).

## Parameters
- `branch` is the branch whose context to bind or unbind: its short name (e.g. `feature/x`) or its full ref (`refs/heads/feature/x`) - both name the same branch. The binding is stored under `refs/heads/<branch>`, the key EDT itself reads for the checked-out branch, so EDT picks the binding up when that branch is checked out, and `update_database` / `get_applications` honour it. A remote-tracking ref (`refs/remotes/...`), any other ref (e.g. a tag), a blank value, or a name git cannot use as a branch is rejected before anything is touched. The branch does not need to be the currently checked-out branch, or even exist yet as a git branch (useful with `create_git_branch`, which can attach a base to a branch's context in the same call it creates the branch).
- `applicationId` comes from `get_applications`; the target application must expose an infobase reference (a plain infobase application, or a standalone-server application wrapping a registered infobase - see `set_infobase_credentials`' notes on the same resolution). An application with neither is rejected, naming the id.
- `action`: `attach` (default) binds the application to the branch context; `detach` removes an existing binding.
- `setDefault` (attach only, default false): also makes the application the branch context's DEFAULT infobase (the one `switch_git_branch`'s bindings read-back and `list_git_branches`' `Default` column report when the context has more than one bound base). Ignored for `detach` - detaching removes the binding regardless of whether it was the default. EDT records a default only for an infobase that is also bound to the CHECKED-OUT branch (it checks the current branch's binding, not the one being changed), so for a branch that is not checked out - unless the checked-out branch already has this base bound - the attach still happens and the call succeeds, but `message` says the default was not recorded and why - check the branch out (`switch_git_branch`) and repeat the attach with `setDefault`. If EDT instead fails to store the default (a platform error, logged to the EDT log), `message` gives EDT's text and no checkout advice. Either way the `bound` read-back shows EDT's actual default: with a single bound base EDT reports that base as `defaultInfobase` even when no default was recorded.

## Behavior
- **attach** uses `InfobaseAssociationSettings.alreadySynchronized(...)`: this RECORDS the binding without triggering any synchronization flow. You are telling EDT "this base is already the right one for this branch", not asking it to run a heavy sync job - the unattended-safe choice (no background Job, no modal).
- **detach** first checks the branch context (`refs/heads/<branch>`) actually has this application bound, and removes it there. If it is not bound there but is bound under the bare short name - a legacy key that older versions of this tool and of `create_git_branch` wrote, and that EDT never reads - that legacy entry is removed instead and `message` says so. If neither has it, the call is rejected with an actionable "not bound" error rather than silently succeeding on a no-op, or leaving you to guess whether the detach did anything.
- On success the result includes a `bound` read-back: `{infobases: [...], defaultInfobase}` for the branch context AFTER the change - proof the base is now bound (attach) or gone (detach). After a legacy entry was removed, the read-back is of that legacy key.

## Notes & gotchas
- **Not gated by the destructive-consent dialog.** This is a pure EDT workspace-metadata write (an association record), not an infobase connection or a destructive model mutation; the binding is trivially reversible with another call.
- **Never opens or authenticates against a 1C infobase.** No connection is made; this only records/removes an association entry.
- The branch **context** and the git branch itself are independent: attaching a binding does not create the branch, and detaching does not delete it. Use `create_git_branch` / `switch_git_branch` for the git side.
- `list_git_branches`' "Application Bindings" table and `switch_git_branch`'s `bindings` read-back are the read-only ways to inspect what this tool changed.
- Bindings that older versions wrote under the bare short name are not migrated automatically. `list_git_branches` lists each one marked `legacy short key - matches no branch`; detach it with this tool, and attach the base again to bind the branch for real.
